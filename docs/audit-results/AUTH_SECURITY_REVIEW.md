# Auth Security Review

**Last audited:** 2026-08-14

## Findings

### 🔵 Low

- **Rate-limit keys trust a client-supplied `X-Forwarded-For` header with no allowlist/validation.** `getClientIp()` in `src/lib/rate-limit.ts` (lines 54-60) takes `request.headers.get("x-forwarded-for")?.split(",")[0]` at face value. This is the standard pattern for platforms like Vercel that overwrite/prepend the true client IP at the edge before the header reaches the app, so it is very likely safe in production as currently deployed — but the code itself does not enforce that assumption (e.g. no check that the request came through a specific trusted proxy, no use of a platform-specific "real IP" header/API). If DevStash is ever run behind a different proxy/CDN, self-hosted without a proxy, or directly exposed, a client could set an arbitrary `X-Forwarded-For` value per request and get a fresh rate-limit bucket every time, defeating the IP-based limiters (`register`, `forgot-password`, `reset-password`) and degrading the login limiter to email-only (still bounded, just weaker than intended).
  - **Fix:** no code change needed if the deployment target is confirmed to be Vercel (or another platform that overwrites `x-forwarded-for` before it reaches the app) — otherwise, source the IP from a platform-specific trusted header/API (e.g. Vercel's `request.ip` equivalent) rather than the general `x-forwarded-for` header, or explicitly document/verify the trust assumption where `getClientIp` is defined.

## Passed Checks

- **`change-password` is now rate limited (fixed on `fix/change-password-rate-limit`).** Added a `changePassword` limiter (5/15min) to `src/lib/rate-limit.ts`, keyed by `session.user.id`, checked in `src/app/api/auth/change-password/route.ts` before the `bcrypt.compare(currentPassword, ...)` call — closing the password-oracle gap flagged in the previous audit. Verified end-to-end against the live dev server signed in as the demo user: 5 wrong-current-password attempts returned the normal 400 error, the 6th correctly returned 429 with a `Retry-After` header; the demo password was left untouched (all attempts used a deliberately wrong current password) and the test Redis key was cleaned up afterward.
- **Rate limiting (new `feature/rate-limiting-auth` work) is sound for the endpoints it covers.** `src/lib/rate-limit.ts` fails open (allows the request) only when Upstash is unconfigured or the `.limit()` call itself throws — this matches the explicit spec requirement (`context/features/rate-limiting-spec.md`: "Rate limiting should fail open... if Upstash is unavailable") and is not a hidden bypass; it's an intentional, documented availability trade-off with no code path that lets a caller force a fail-open (e.g. no way to make Upstash "unreachable" from outside).
- **Login limiter (`login`, 5/15min, keyed `${ip}:${email}`) is enforced inside `authorize()` in `src/auth.ts` before any DB lookup or password comparison**, so a rate-limited attacker never gets a timing or existence signal from the user-lookup/bcrypt-compare path, and the limiter can't be bypassed by hitting a different NextAuth-internal entry point since `authorize()` is the sole credentials-validation function.
- **`register`, `forgot-password`, `reset-password`, `resend-verification` all check the rate limit before touching the database or sending email**, and correctly return `429` with a `Retry-After` header (`rateLimitResponse()`), matching the spec.
- **Anti-enumeration is intact and consistent across all four relevant endpoints:** `register` returns an identical `{ success: true }` for a duplicate email as for a real signup (`src/app/api/auth/register/route.ts` lines 44-49); `forgot-password` and `resend-verification` always return generic success regardless of account existence, verification status, or OAuth-only status, only conditionally sending email server-side.
- **Password hashing remains bcrypt at 12 rounds consistently** across register, reset-password, and change-password — no regressions introduced by the rate-limiting change.
- **Token security (email verification + password reset) unchanged and still correct:** 256-bit (`crypto.randomBytes(32)`) tokens, 24h TTL, single-use (deleted on consumption, and re-deleted/replaced on a fresh request via `deleteMany` before create), password-reset tokens namespaced (`password-reset:${email}`) so they can't collide with or wipe a pending verification token for the same address, and reset attempts against OAuth-only accounts (`!user.password`) are clearly rejected rather than silently creating a password.
- **`jwt` callback's password-change invalidation still works correctly with the new rate-limit code path** — `RateLimitedError` is thrown before any user/session data is touched, so a rate-limited login attempt can't produce a token that later gets invalidated unexpectedly, and successful logins after a password change still correctly invalidate stale JWTs from other sessions (`src/auth.ts` lines 47-63).
- **`proxy.ts` continues to gate `/dashboard` and `/profile` correctly** and is unaffected by the rate-limiting change (it doesn't touch the Credentials provider's `authorize()` path).
- **Profile page and its mutations remain correctly session-scoped:** `profile/page.tsx` redirects on missing session/user; `change-password` and `delete-account` both derive the target user from `session.user.id` (never a client-supplied id); `change-password` still verifies `currentPassword` via `bcrypt.compare` before accepting a new one; `delete-account` requires typed `DELETE` confirmation client-side and only ever deletes `session.user.id`.
- **GitHub OAuth account linking is safe by default** — no `allowDangerousEmailAccountLinking` override in `src/auth.config.ts`, so a GitHub sign-in cannot silently take over an existing email/password account with the same email address (NextAuth v5's default, unmodified here).
- **`SignInForm.tsx` surfaces the new `rate_limited` error code without leaking any account-existence information** — the message ("Too many attempts...") is identical regardless of whether the email exists, mirroring the existing `email_not_verified`/generic "Invalid email or password" handling.
